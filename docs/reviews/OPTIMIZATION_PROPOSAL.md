# Tangent-Timetable 工程与架构分析及优化方案

## 1. 结论

当前工程由 Spring Boot / MyBatis-Plus 后端、React 前端，以及 WinForms + WebView2 桌面壳组成。Web 版使用 MySQL；桌面版启动本机后端并使用 H2 文件数据库。Web 和桌面复用同一套前端与业务 API，AI SSE、AI 操作预览确认和循环待办是主要的跨层功能。

建议继续采用**模块化单体**，暂时不拆微服务。当前规模下，拆服务会增加部署、数据一致性和调试成本，却不能解决已经发现的边界问题。先把“用户/课表数据边界、确认后写入的一致性、桌面端本地信任边界、数据库版本管理”固化，再逐步整理模块和体验。

本方案基于项目提交 **d39580b**（桌面版代码基线 8f4f686）对源代码、配置、SQL 和现有问题清单进行静态审阅。没有连接生产数据库，也没有启动应用或运行测试；并发、网络监听、实际 WebView 导航等事项应在修复验收时复现。报告把这类情况标为“风险/待验证”，不当作已经复现的运行故障。

## 2. 当前结构与已有基础

主要调用链：

- Web：浏览器 → React 页面与 AppContext → REST / SSE → Controller → Service → Mapper → MySQL。
- 桌面：WinForms 壳 → 本机 Java 后端（standalone profile）→ H2 文件库；WebView2 加载本机后端托管的前端。
- AI：前端建立对话和 SSE 请求 → 后端构造上下文并调用模型 → 将回复和待确认操作落库 → 用户确认后执行 → 前端刷新数据。
- 循环待办：每分钟调度扫描 → 固定规则或 Rhino 脚本求值 → 创建待办；固定频率路径已有数据库唯一键和领取/去重处理。

已经值得保留的设计：桌面数据留在用户目录；AI 写操作设计为预览、确认后执行；课程和考试归属课表；固定循环任务有数据库去重；Web 和桌面共用前端，减少两套产品行为漂移。

当前主要薄弱点是：AI 操作没有统一的“课表工作区”强约束；PENDING 操作缺少原子领取；一些跨实体生命周期靠手工删除；桌面壳对子进程和导航目标的信任边界不够明确；MySQL 与 H2 的 schema 靠人工同步；产品代码和现有测试对关键业务边界覆盖有限。

### 优先建议的回归用例

先围绕 B1–B6 建立可重复的测试夹具：双课表所有权测试、AI action 并发确认、非法提案持久化、课表删除后的关联清理、人工/AI 完成循环待办的一致性。随后补充桌面端伪端口/外部导航安全验证，以及自定义规则的固定时钟边界用例。现有测试数量有限，回归测试应按真实业务边界设计，不要只验证 DTO 或 mock 返回值。

## 4. 架构优化方案

### 4.1 保留单体，按业务边界收敛模块

当前最适合的是模块化单体。逐步把 controller 之间的业务编排移入应用服务，建议形成以下边界：

- **Schedule**：课表、课程、考试、节次配置；统一负责 schedule ownership 和学期周数。
- **Todo**：待办、重复规则、考试待办联动；统一完成/下一期事务。
- **AI**：对话、模型配置、提案解析、提案状态机；只通过 Schedule/Todo 应用服务做写入。
- **Identity/Security**：API Key 验证、角色与用户资料；API 响应 DTO 不回传凭据。
- **Desktop Runtime**：桌面后端启动、H2 数据目录、loopback 服务、密钥保护和升级/备份。

跨模块统一传递 WorkspaceContext（账号身份 + 可选或必需课表）。当前用户 Key 不应由每个 Service 自行拼接过滤条件，否则同一账号下的课表边界容易在新增入口遗漏。

### 4.2 为 AI 写操作建立明确状态机

把 action 状态明确为：

**PENDING → EXECUTING → EXECUTED**

异常时按可重试性进入 **FAILED_RETRYABLE** 或 **FAILED_FINAL**；数据快照过期进入 **STALE**；用户拒绝进入 **REJECTED**。领取通过数据库条件更新原子完成，状态转换、目标数据写入和完成状态同一事务；外部模型调用放在事务外。每个 action 保存 scheduleId、作用范围、指纹/版本和幂等键。前端只展示可执行状态，重复提交得到清楚的冲突响应。

不要单靠数据指纹替代权限检查：指纹判断“数据是否变了”，WorkspaceContext 才决定“是否有权改这条记录”。

### 4.3 用版本化迁移替代启动时建表

当前 CREATE TABLE IF NOT EXISTS 和手工同步 schema.sql / schema-h2.sql，不能追踪已安装用户的结构版本。引入 Flyway 等数据库迁移工具：

1. 先比对 MySQL 与 H2 的线上/交付 schema，确定一份可信的当前基线。
2. 对已有 MySQL 数据库做显式 baseline；先备份并在副本上演练，不对未知库自动 baseline。
3. 后续结构改动只追加版本化迁移；H2 与 MySQL 的差异按数据库 profile 分开维护，并在 CI 对两种目标都应用迁移。
4. 参考数据单独管理；生产迁移采用先加列/回填/校验/再约束的兼容步骤。

Flyway 对既有库的基线概念与首次迁移行为见官方 [Baseline 文档](https://documentation.red-gate.com/flyway/reference/commands/baseline)。迁移工具不能自动修复历史不一致，因此第 1、2 步必须先完成。

### 4.4 明确桌面与服务器的配置/安全边界

DeepSeek Key 当前由本机 DeepSeekKeyStore 管理，而 AiController 的配置接口受 API Key 认证但不是独立管理员角色保护。单机桌面形态下这是全局配置；多用户 Web 形态下任何合法账号都可能影响共享配置。建议把接口拆分为：

- 桌面本机设置：只允许 loopback、绑定桌面安全策略、密钥用 Windows DPAPI 保护。
- Web 服务设置：只允许显式管理员角色；服务器密钥保存在部署密钥管理/受保护环境配置中。
- 用户偏好：仅存每用户非秘密设置。

桌面账号 Key 目前以明文文件保存并经 Java 命令行参数传给子进程。建议改为 DPAPI 加密存储，并通过受保护的短期本机通道传递 bootstrap secret，避免明文命令行暴露；设置数据目录 ACL。API 响应模型使用专用 DTO，不序列化 apiKey 字段。

### 4.5 统一时钟、时区和后台任务容量

对业务服务注入 Clock，明确产品时区（当前配置意图为 Asia/Shanghai），调度计算、时间展示与 JDBC 时间约定一致。自定义脚本上下文应有明确时间语义。

Spring 定时扫描应配置有界线程池、运行耗时和失败计数。固定/自定义规则在多实例 Web 部署时要依靠数据库原子领取或分布式锁，不能假设每个实例只会执行一次。桌面 H2 单实例可以使用相同接口的本地实现。

### 4.6 规范 API 与长任务取消

- 后端实体与外部 API DTO 分离，不直接返回 Mapper Entity。
- 列表接口增加分页、过滤和最大 pageSize；当前全量列表不应随历史数据无限增大。
- 为 AI SSE 设置连接/读取空闲超时，前端组件退出或切换对话时发 AbortController；后端把取消信号传播到模型 HTTP 请求并在落库前再次检查。
- SSE 代理部署说明增加 buffering、read timeout 和连接保持要求，并用真实 Nginx 配置验证。

Spring 事务要覆盖明确的业务写边界；默认回滚规则等细节需结合异常类型确认，不能把 Controller 多次调用拼在一起当作一个原子动作。参考 [Spring @Transactional 文档](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)。

| 方向 | 建议 | 用户可见收益 / 边界 |
|---|---|---|
| 数据安全 | 首次启动展示并提供轮换/导出账号恢复方式；H2 自动备份并提供恢复前预览；桌面 Key 改 DPAPI；日志脱敏。 | 换机或数据库损坏时可恢复；避免将备份、日志和密钥文件一并泄露。 |
| AI 可控性 | 确认卡片展示目标课表、影响记录数、关键字段差异；批量删除/改动显示逐条清单；过期提案明确要求重新生成。 | 用户在提交前可以判断 AI 改的是哪张课表以及具体什么内容。 |
| 课表导入 | 解析后先展示错误行、冲突、超范围周次和重复课程；支持只导入有效行或取消。 | 降低导入后逐条修复成本；服务端仍需重复校验。 |
| 提醒体验 | 将“截止时间倒计时”与“系统通知”区分；如果产品承诺提醒，再实现可配置的桌面通知/权限与静默时间。 | 避免只显示页面内倒计时却让用户误以为会在后台通知。 |
| 节次管理员 | 明确全局节次是否适合多学校/多学期；如不适合，改为课表级模板并支持复制。 | 不同课表可使用不同作息，不互相覆盖。 |
| 可观测性 | 给模型调用、SSE 首 token/总耗时、循环任务积压和数据库迁移增加结构化指标；关联请求 ID，但不记录密钥、完整 prompt 或敏感内容。 | 出现“AI 卡住/重复提醒/数据没刷新”时能定位阶段而不泄露内容。 |
| 发布维护 | 固定 .NET、Java、Node 与 WebView2 Runtime/SDK 版本；桌面构建校验依赖版本和产物清单，生成哈希；CI 增加桌面构建和迁移检查。 | 构建可复现，交付文件发生变化可追踪。 |

## 6. 推荐实施顺序

| 阶段 | 工作范围 | 完成标志 |
|---|---|---|
| 第一阶段：安全与数据边界 | B1 桌面导航/端口信任、B2 action 原子领取、B3 工作区授权与指纹隔离、B4 提案校验、B12 服务端角色鉴权。 | 错误 origin 无法拿到凭据；普通用户不能改全局配置；同一 action 只能写一次；跨课表读写被拒；无效模型结果不破坏旧提案。 |
| 第二阶段：领域一致性 | B5 课表删除关联清理、B6 统一待办完成流程、B7 自定义循环规则窗口语义。 | 删除和完成均为单事务；循环触发在延迟、重试和多实例条件下符合定义。 |
| 第三阶段：工程可维护性 | Flyway 基线/迁移、DTO 和参数校验、分页、Clock/时区、受限调度线程池、取消链路。 | H2/MySQL 可从空库和升级库重复部署；关键边界有自动回归覆盖。 |
| 第四阶段：体验与交付 | AI 差异预览、导入诊断、备份恢复、桌面通知（若产品需要）、固定工具链和发布校验。 | 有可理解的用户反馈和可操作恢复流程；桌面构建与运行手册可复现。 |

实施时先建立可复现的业务测试夹具，再逐项修复。数据库迁移先在数据副本演练；桌面安全更改需同时覆盖开发版和打包版。每项只有在相应验收用例通过后，才能从“建议/待验证”改记为“已修复”。
