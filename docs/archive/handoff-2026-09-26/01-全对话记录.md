### 2.2 严重（CRITICAL）

**A1. Rhino 沙箱的超时无法终止脚本 —— 每次请求泄漏一个永久占满 CPU 的线程**

超时检查只写在 `observeInstructionCount`（`RecurringScriptEvaluator.java:80`），而 Rhino 只在 JS 字节码的
**指令边界**调用它。任何**单次原生（Java）调用**（正则、大分配）全在 Java 内部执行，永不经过边界。
失败路径只 `join(TIMEOUT_MS+500)` 后打印 `abandoning thread` 就返回 —— **线程永不停止**。

自建 PoC（针对仓库已编译的类 + rhino-1.7.14）实测：

| 脚本 | `test()` 返回 | 之后 |
|---|---|---|
| `while(true){}` | 341 ms，被指令计数中断 | 线程已死，CPU 平稳 ✅ |
| `/(a+)+$/.test(s)` | 2013 ms，返回"脚本执行超时" | **1 个线程 RUNNABLE 卡在 `NativeRegExp.executeREBytecode`，每秒烧 ~1000 ms CPU，永不结束** ❌ |

后续进一步用 `RegexVectors` 探针穷举了入口，得到关键数据：

| 正则入口 | 是否泄漏线程 |
|---|---|
| 正则字面量 `/(a+)+$/` | **是** |
| `new RegExp(str)` | **是** |
| `String.match(str)` | **是** |
| `String.search(str)` | **是** |
| `String.split(str)` / `String.replace(str)` | 否（2 ms，安全） |
| `while(true){}` | 否（被指令计数中断） |

**可达性**：`POST /api/recurring-todos/test-script`（`RecurringTodoController.java:80-89`）无管理员校验、无限流，
任何有效 Key 都能循环触发；保存规则与调度器每 60 秒的 CUSTOM 扫描也走同一求值器。

**A2. 一个可用凭据被提交进仓库、每次启动自动重建、并被打进前端产物**

`data.sql:1` 写入 `demo-key-001`，配合 `spring.sql.init.mode: always` **每次启动重建**（删了也没用）；
前端 `WidgetPreviewPage.tsx:75` 还硬编码 `key || getApiKey() || 'demo-key-001'` 作为兜底。

## 7. 第 7 轮：登录页那句话是什么意思

**你的输入**：`输入管理员分配给你的 API Key 以进入你的课程表与待办空间。是什么意思`

**解释**：这个应用**没有注册页、没有用户名密码、也没有管理员后台**。一个账号就是 `api_key` 表里的一行
（一串字符串 + 一个 `label` 显示名）。"管理员分配给你"= 部署者预先在数据库里建好这行。
输入后前端调 `GET /api/auth/verify` 校验，通过则存进 `localStorage`，之后每个请求带 `X-API-Key` 头；
后端 `ApiKeyInterceptor` 据此认定你是谁，Service 层所有查询按 `api_key` 过滤 —— 这就是"你的空间"。

**我现场演示了隔离**：新建一个 Key `my-key-2026`，它的 `schedules`/`todos` 都是空，
访问别人的课表 id 得到 **`404 课表不存在`**（刻意不暴露"存在但不属于你"）。

## 12. 第 12 轮：界面分辨率很低

**你的输入**：`界面的分辨率很低`

### 12.1 根因

| 检测项 | 结果 |
|---|---|
| 屏幕原生分辨率 | **3072 × 1920**（200% 缩放，等效 1536×960） |
| 进程 DPI 感知（`GetProcessDpiAwareness`） | **0 = UNAWARE** ← 根因 |

进程没有 DPI 感知声明时，Windows 会把**整个窗口位图放大 2 倍**，文字与 WebView 内容都发虚。

### 12.2 修复

1. 新增 `desktop/shell/app.manifest`：`permonitorv2` / `permonitor` / `true/pm` 逐级回退；
2. `Main` 里再调用 `SetProcessDpiAwarenessContext` 兜底（清单被忽略时仍生效）；
3. 随包发布 `TangentTimetable.exe.config`（WinForms 的 PerMonitorV2 需要该开关）；
4. 窗口尺寸按窗口所在显示器 DPI 换算，并用 `SetWindowPos` 落物理像素；
5. `build-desktop.ps1` 接入清单与 exe.config。

### 12.3 验证（含一次自己的误判）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 进程 DPI 感知 | 0 = UNAWARE | **2 = PER_MONITOR_AWARE** |

**过程中的一次误判值得记录**：我一度以为窗口尺寸仍然没生效 —— 因为外部量到的始终是 1180×820。
在程序里加临时诊断后发现程序**算得完全正确**（`dpi=192 scale=2 size=2360x1640`）。
真相是：**我的测量进程自己是 DPI 不感知的，`GetWindowRect` 对它返回的是被虚拟化的坐标（200% 下除以 2）**。
改用 DPI 感知的测量器复核：

```
大切课程表 | physical=2360x1640 | dpi=192 | logical=1180x820
```

即窗口一直是正确的物理尺寸。**结论：当测量工具与被测对象对 DPI 的认知不一致时，测量结果不可信** ——
这类"修复"最容易越修越坏。
