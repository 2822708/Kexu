## 二、严重（CRITICAL）

### A1. Rhino 沙箱的超时无法终止脚本 —— 每次请求泄漏一个永久占满 CPU 的线程

**位置：** `backend/src/main/java/com/timetable/service/impl/RecurringScriptEvaluator.java:38-50, 64-90, 139-151`

超时检查**只**存在于 `observeInstructionCount` 内部（第 80 行）：

```java
if (System.currentTimeMillis() - startOf(cx) > TIMEOUT_MS) {
    throw new ScriptAbortError("脚本执行超时");
}
```

Rhino 只在 JS 字节码的指令边界调用该观察器。任何**单次原生（Java）调用** —— 正则、大数组分配、大字符串操作 —— 全部在 Java 内部执行，永远不会经过指令边界，因此该检查永不触发。而失败路径根本不停止线程（第 145-148 行）：

```java
if (worker.isAlive()) {
    log.warn("Recurring script did not finish in time, abandoning thread");
    return new ScriptResult(false, false, "脚本执行超时（上限 " + TIMEOUT_MS + "ms）");
}
```

**实测证据（针对仓库已编译的类运行，未修改仓库）：**

| 提交的脚本 | `test()` 返回 | 之后的状态（线程 + 进程 CPU） |
|---|---|---|
| `function shouldTrigger(ctx){ while(true){} }` | 341 ms，被指令计数中断 | 0 个脚本线程，CPU 平稳（3 秒内 812 ms → 828 ms） |
| `function shouldTrigger(ctx){ var s='aaa…!'; /(a+)+$/.test(s); return true; }` | 2013 ms，返回 `脚本执行超时（上限 1500ms）` | **1 个线程存活，状态 `RUNNABLE`，栈顶 `org.mozilla.javascript.regexp.NativeRegExp.executeREBytecode`，每秒稳定消耗约 1000 ms CPU，永不结束** |

`while(true)` 的对照组证明指令计数本身是有效的、测试装置是可靠的 —— 漏洞精确地出在原生执行上。

另一位审计者用不同工具链（jshell、`-Xmx512m`）对同一个 `rhino-1.7.14` 制品独立复现，测得正则求值期间 **`ticks=0`**（零次指令检查点），而 `while(true){}` 在 108 ms 内被中断。

**严重度校准：这是拒绝服务，不是代码执行。** 我另行验证了 Java 桥接被完全关闭（见第六节），因此沙箱无法逃逸 —— 缺陷在于它**停不下来**。

**影响：** 一个很小的请求体即可永久占用一个 CPU 核心，且每次请求再泄漏一个线程。JVM 无法安全抢占运行中的线程，因此该泄漏在进程生命周期内不可回收。

**可达性：** `POST /api/recurring-todos/test-script`（`RecurringTodoController.java:80-89`）没有管理员校验、没有限流 —— 任何有效 API Key（包括随包发布的 `demo-key-001`）都能循环触发。保存规则时（`RecurringTodoServiceImpl.java:85-92`）与调度器对 `CUSTOM` 规则的每 60 秒扫描（`:208-216`）也会走到同一个求值器。

**修复：** 保留指令计数是必要条件而非充分条件。由于无法安全抢占一次原生调用，真正的保证只有把不可信脚本移出请求/调度 JVM —— 在可强杀的独立进程（或 isolate）中求值，并限制并发数。若短期内做不到，至少：静态拒绝含正则字面量等无界原生构造的脚本、对求值并发数设硬上限，并把线程泄漏作为已知代价明确记录。另需为内存炸弹与原生调用两种情形补测试 —— 现有 9 个测试一个都没覆盖。

### A2. 一个可用凭据被提交进仓库、每次启动自动重建、并被打进前端产物

**位置：** `backend/src/main/resources/db/data.sql:1`、`application.yml:8-12`、`frontend/src/pages/WidgetPreviewPage.tsx:75`、`frontend/src/pages/LoginPage.tsx:54`


配合 `spring.sql.init.mode: always`（`application.yml:10`），即使运维删掉该行，**每次启动都会被重建**。该 Key 还被硬编码进 SPA 产物，作为小组件兜底凭据：

**影响：** 任何读过这个公开仓库的人都持有一个有效登录凭据，对默认账号的课表、课程、待办、考试、AI 对话拥有完整读写权。任何把真实数据留在默认账号下的部署 —— 或以为"删掉那一行就没事了"的部署 —— 都是暴露的。小组件接口还接受把 Key 放在 URL 路径里，连请求头都不需要就能读。

## 三、高危（HIGH）

### B1. "提案失效"指纹在**调用模型之后**才计算，基线取错时刻

**位置：** `AiServiceImpl.java:399-408`（读取数据）→ `:418`（组装 Prompt）→ `:471/:475`（调用模型）→ `:507-511`（把列表传给落库）→ `:554`（`_before` 用这些列表）→ **`:568-569`**（指纹）

```java
action.setDataFingerprint(
        fingerprintCache.computeIfAbsent(scope, sc -> fingerprintOf(sc, scheduleId, apiKey)));
```

`fingerprintOf`（第 250-285 行）**会重新查库**，所以落库的哈希是**模型调用之后**的状态，而 Prompt 和用户确认的 `_before` 快照来自调用**之前**读取的列表。

**影响：** 模型调用的 30–120 秒内发生的任何变更 —— 同一用户开了另一个标签页、`RecurringTodoScheduler` 插入了待办、`ExamTodoScheduler` 完成了待办 —— 都已被写进基线。于是 `executeAction` 的复查（第 786-795 行）会通过，一个基于旧数据推理出来的提案会被施加到新数据之上。这正是文档中的"提案失效机制"（`AGENTS.md:429-449`）本该覆盖的时间窗，而 `invalidateProposalsOnDataChange` 帮不上忙，因为此时 action 还不存在。此外差异卡展示的是调用前的旧值，而哈希编码的是调用后的新状态，两者互相矛盾。

**修复：** 在组装 Prompt 时用**已经加载好的那些列表**计算指纹并随 action 一起存储，绝不在 `persistAssistantResult` 中重算。

### B2. 小组件凭据走 URL 路径，且 `/api/widget/**` 绕过了认证拦截器

**位置：** `WidgetController.java:34-46`、`config/WebMvcConfig.java:21`、`frontend/src/pages/SettingsPage.tsx:57`

该接口被排除在拦截器之外，改为从路径变量手工认证；同时 UI 把原始 Key 渲染成一个可复制、可分享的 URL。Key 就是账号凭据，因此会落入 nginx 访问日志、浏览器历史、以及小组件页面的 `Referer`。

**修复：** 改用 `X-API-Key` 请求头（交给现有拦截器处理），或签发短期只读令牌；绝不在 UI 里展示账号 Key。结合 A2，这是全应用中最廉价的读数据外泄路径。

### B3. 客户端断连无法被感知，被遗弃的 AI 流会耗尽线程池且仍然落库

**位置：** `AiController.java:106-158`（任何地方都没有注册 `onCompletion`/`onTimeout`/`onError`）、`AiController.java:43-51`、`frontend/src/api/stream.ts:19,29`、`frontend/src/pages/AiChatPage.tsx:266`

`emit()` 吞掉 `IOException | IllegalStateException`（第 155-157 行）且不返回任何信息，读循环无从得知客户端已离开。没有任何机制取消上游 DeepSeek 调用；`ai-stream-N` 线程会跑完（默认 `timeout-seconds: 120`），然后**仍然把 assistant 消息和 PENDING 提案写进库**（第 132 行）。前端接受了 `signal` 参数却从不传入（`frontend/src` 全量 grep：`AbortController` 零命中）。

**影响：** 约 17 个被遗弃的流（开着的标签页／刷新／路由跳转）即可占满 16 线程池，之后所有用户都收到 `503 当前 AI 请求过多`。此外还白白消耗模型费用。

**修复：** 注册 `emitter.onCompletion/onTimeout` 以取消上游调用（`sendAsync` + `CompletableFuture`）；让 `emit` 返回失败信号，使读循环能主动退出；`AiChatPage` 传入 `AbortSignal`，在卸载与切换会话时 abort。

### B4. AI 流线程池实际只有 4 并发，其余静默排队；注释与代码自相矛盾

**位置：** `AiController.java:42` 对比 `:43-51`

```java
// 有界线程池：限制并发流式任务，队列满时由调用线程执行以形成背压，避免无限创建线程
... new ThreadPoolExecutor(4, 16, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(64), ..., new ThreadPoolExecutor.AbortPolicy());
```

两处缺陷：注释描述的是 `CallerRunsPolicy`，实际策略是 `AbortPolicy`；并且由于 `corePoolSize=4` 搭配 64 槽队列，`ThreadPoolExecutor` **最多只会创建 4 个线程** —— 第 5–16 个线程只有在队列彻底填满后才会创建。因此第 5…68 个请求在队列里静默等待，不产生任何 SSE 事件，最长可能等到 300 秒的 emitter 超时，期间一无所获。

**修复：** 设 `corePoolSize = maximumPoolSize = 16`（或 `allowCoreThreadTimeOut(true)`），队列取小，并显式发出排队中／`error` 事件，避免等待中的客户端面对空白。同步修正注释。

### B5. 循环待办调度器没有锁、没有占位（claim）、没有唯一约束 —— 同一次触发会生成重复待办

**位置：** `RecurringTodoServiceImpl.java:228-255` 与 `:196-226`；`RecurringTodoScheduler.java:27-46`；`schema.sql:112-131`

纯粹的 `selectList` → `spawnTodo`（INSERT）→ `updateById`，没有条件占位、没有 `SELECT … FOR UPDATE`、没有版本列、没有唯一键 —— schema 里只有 `INDEX idx_recurring_next (enabled, next_trigger_at)`（第 130 行）。

两次重叠的扫描会为同一次触发产生重复待办，而这种重叠**在单进程内即可发生**：`@Scheduled(fixedDelay = 60_000)` 的首次执行随 `ContextRefreshedEvent` 立即开始，而 `catchUpOnStartup` 在 `ApplicationReadyEvent` 时于主线程执行（`RecurringTodoScheduler.java:36-46`）。多实例部署则必然发生。`triggerNow`（`:151-162`）也无条件生成，因此"立即触发"与并发扫描（或双击）同样会重复。

**修复：** 用条件更新占位 —— `UPDATE recurring_todo SET next_trigger_at = ? WHERE id = ? AND next_trigger_at = ?`，仅在恰好影响 1 行时才 INSERT；给 `todo(recurring_id, ddl)` 加唯一索引；多实例部署用 ShedLock 或选主。

### B6. 调度器把过期的规则实体整体写回 —— 用户修改被静默回滚，已停用的规则被复活

**位置：** `RecurringTodoServiceImpl.java:236, 251-252, 160, 221, 214-215`

```java
for (RecurringTodo rule : recurringMapper.selectList(wrapper)) {   // 快照在此刻读取
    ...
    rule.setNextTriggerAt(due);
    recurringMapper.updateById(rule);                              // 写回该实体所有非 null 字段
}
```

`updateById` 持久化整个扫描前快照，而不只是预期修改的列。

**影响：** 用户在扫描进行中修改规则的标题／触发时刻，或**停用**规则时，修改会被旧快照覆盖 —— 而用户刚刚停用的规则会被**复活成 `enabled = true`**，继续生成待办。脚本报错自动停用路径（`:214-215`）与 `triggerNow`（`:160`）存在同样的整行写回。

**修复：** 只更新目标列，就像删除路径已经做的那样（`:129-132`）：`lambdaUpdate().eq(RecurringTodo::getId, id).set(RecurringTodo::getNextTriggerAt, due).set(RecurringTodo::getLastTriggeredAt, ...)`；并加 `@Version` 乐观锁。

### 正确性 / 数据完整性

**C1. 未绑定课表的 AI 对话会让工作空间校验失效，且破坏性 COURSE 操作跳过了课表校验。**
`createConversation` 允许 `scheduleId == null`（`AiServiceImpl.java:121-129`）；而工作空间不一致校验要求**两边都非 null**（`:392-393`），因此未绑定的对话在后续每条消息里都接受任意 `scheduleId` 且不报错，绑定只在模型调用之后才写入（`:581`）。更严重的是，COURSE 作用域指纹退化为常量哈希 `"Snull|"`（`:250-254`），而 `DELETE_COURSE` / `UPDATE_EXAM` / `DELETE_EXAM` 都不调用 `requireSchedule()`（只有 `CREATE_COURSE`/`UPDATE_COURSE`/`CREATE_EXAM` 调用了）。`courseService.delete(id, apiKey)` 只校验课程所属课表属于同一 API Key，因此 AI 编造或猜中的 id 可以删掉该用户**任意课表**下的课程，而卡片因为 `_before` 只取工作空间课表，只显示 `目标 ID：N`。

*修复：* 所有 COURSE 作用域操作都强制要求课表；把课表 id 存到 action 上；修改前校验目标行的 `schedule_id`/`api_key`；给出明确错误而不是静默继续。

**C2. 同一条提案可被并发执行两次。** `executeAction`（`:764-807`）是 查询 → 校验 → 执行 → `updateById`，没有条件更新，`ai_action` 也没有版本列。两个并发的 `POST .../execute` 都会读到 `PENDING` 并各自施加写入（重复建课／建待办，或来回切换）。两个标签页或一次 HTTP 重试就够。
*修复：* 在 `applyAction` **之前**执行 `UPDATE ai_action SET action_status='EXECUTED' WHERE id=? AND action_status='PENDING'`，影响 0 行则中止（或用 `@Version`/`SELECT … FOR UPDATE`）。

**C3. 失效逻辑没有按工作空间隔离，并且会给"早于被执行提案生成"的兄弟提案刷新指纹。** `invalidatePending` 只按 `apiKey + scope + status` 过滤（`:305-318`），因此会话 A（课表 A）产生新提案会把会话 B（课表 B）里 PENDING 的 COURSE 提案标记为 STALE。而 `invalidateOtherScopePending`（`:830-851`）会刷新所有"更晚创建"的兄弟提案 —— `:821-822` 的理由（"生成时已看到更新后的数据"）对于那些**在被执行提案之后生成、却在执行之前就已存在**的提案并不成立，于是"先执行 `UPDATE_COURSE(id=5, name=X)`，再执行更早生成的 `UPDATE_COURSE(id=5, name=Y)`"会静默回滚，且把其他字段一并写回执行前的旧值。
*修复：* 失效按 `(apiKey, scope, scheduleId)` 隔离；用 `created_at` 而非 `id` 判断先后；不要跨会话刷新基线。

**C4. 非法提案会被落库成可点击卡片，并连带作废合法的待确认提案。** 任何未知 `type` 都会被存成 `PENDING`（`:541-545`），经子串启发式归入作用域（`scopeOf`：`:242-244`），并渲染出「确认执行」按钮，直到点击时才报 `400 不支持的操作类型`（`:961`）。已知 type 但 `data` 缺失／为空也一样（`:971-979`）只在执行时才发现。更糟的是 `:576-578` 会在插入新提案**之前**把该作用域内所有 PENDING 提案标为 STALE，于是一条垃圾提案就毁掉了用户合法的待确认提案。
*修复：* 插入前校验 `type` 属于已知集合，并 dry-run 校验必需字段；直接丢弃非法节点；只有确实产生了合法提案的作用域才做失效。

**C5. Prompt 体积无上限。** `AiPromptBuilder.java:204-273` 每轮都会拼入全部课程、考试、待办、循环规则（含完整脚本）；历史是 20 **条消息**（`:63`、`:420-422`），但每条 assistant 消息都带着完整 action 数据重放。用户记录积累到一定程度后，每轮都会超出上下文窗口并以笼统的 502 失败 —— 而用户消息此时已经落库。整条链路上没有任何截断、摘要或"上下文过大"分支。
*修复：* 每个区块按记录数／字符数设上限并给出截断提示；历史按 token 预算分页。

**C6. 截断被当作成功，并把原始 JSON 当成回复展示给用户。** `DeepSeekClientImpl.java:149-156` **只在什么都没收到时**（`full.length() == 0`）才检查 `finish_reason`，因此被 `max_tokens` 截断但有部分内容时会被当作正常返回；`parseJson` 随后无法解析半截 JSON，降级为把原始片段当正文回显（`AiServiceImpl.java:621-627`）—— 它被持久化为 assistant 消息并渲染进气泡，同时静默丢弃已完成的部分 actions。完整原始输出（可达约 16k token）还会被塞进 WARN 日志（`:622`）。
*修复：* 独立于 `full.length()` 检查 `finish_reason`；解析失败时提取 `text` 字段或给出友好提示，而不是回显原始载荷；日志只打截断前缀。

**C7. 流式非 2xx 路径泄漏 `InputStream`。** `DeepSeekClientImpl.java:108-112` 在状态码非 2xx 时既不消费也不关闭 `response.body()`，因此每次上游 4xx/5xx（最常见的是 429）连接都不会归还连接池；错误体也既没记录也没上抛。成功路径的 try-with-resources 是正确的。
*修复：* 用 `try (InputStream in = response.body())` 包住状态判断，并记录有限长度的错误体前缀。

**C8. 上游卡死会钉住一个工作线程；120 秒超时覆盖不到响应体传输阶段的停顿。** `DeepSeekClientImpl.java:88` 设置的是 `HttpRequest.timeout`，但 Java 的请求超时是针对**收到响应**而言；对 `BodyHandlers.ofInputStream()`，响应头之后的停顿不受该超时约束，而阻塞式的 `readLine()` 循环（`:116-147`）没有任何空闲超时。`SseEmitter` 的 300 秒超时只关客户端一侧。*置信度：JDK 语义为推测；"完全没有读超时"已确认。*

**C9. `ExamTodoScheduler` 每分钟重扫全部历史考试，且统计口径错误。** `ExamTodoScheduler.java:58-77` 每轮加载全部 `exam_date <= today` 的考试（随部署时长无界增长），并对每场已结束考试都 `completed++`，无论是否真的更新了待办，因此启动日志 "completed N exam-linked todo(s)" 是误导性的。两个调度器也都没有多实例保护。

**C10. `RecurringTodoServiceImpl.delete` 缺少租户过滤（潜在，当前不可利用）。** 第 124-133 行仅按 `recurringId` 更新待办，没有 `apiKey` 谓词。我已验证**当前不可利用**：`TodoRequest` 没有 `recurringId` 字段（`dto/TodoRequest.java:8-18`），而 `setRecurringId` 只在 `spawnTodo`（`:176`，用的是规则自身的 id **和**自身的 apiKey）中被调用，或被置为 null。仍建议补上 `.eq(Todo::getApiKey, apiKey)` 作为租户守卫。

**C11. 考试变更从不触发提案失效；而调度器写入又会造成误报 409。** `ExamController.java:28-42` 漏掉了 Course/Todo/Recurring 控制器都有的 `invalidateProposalsOnDataChange` 调用，因此手工改过考试（同时会写入／更新考试关联待办）之后，COURSE/TODO 卡片仍显示「待确认」，点击才失败 409。反过来，TODO 指纹把调度器生成的待办也算进去，于是规则触发或考试结束会让用户**什么都没改**的待确认提案失效。

**C12. 用户消息在调用模型之前就落库。** `AiServiceImpl.java:410-414` 先插入用户轮次，再调用模型（`:469-496`）。任何 502 都会留下一个没有回复的用户轮次；前端在出错时会恢复输入框（`AiChatPage.tsx:293`），于是重试会把同一条指令再存一遍，模型看到两个相同的用户轮次。

### 调度器、循环规则与校验缺陷

**C23. 脚本内存哨兵度量的是整个 JVM，无关分配会永久停用一条正常规则。** `RecurringScriptEvaluator.java:73-78` 比较的是 `Runtime.totalMemory() - freeMemory()`（进程级）。任何并发的 64 MB 分配 —— 一个大结果集、另一个 AI 响应 —— 都会中断一条正确脚本，而中断路径随后把规则永久置为 `enabled = false`（`RecurringTodoServiceImpl.java:210-217`），用户看不到任何原因。反向问题同样存在：无关对象被 GC 会掩盖脚本自身的增长。*修复：* 按次评估归因内存（独立进程 + 自己的 `-Xmx`）；基础设施类中断绝不自动停用规则，只有真正的脚本错误才停用。

**C24. 两个调度器共用 Spring 的单个默认调度线程。** `RecurringTodoScheduler.java:27` 与 `ExamTodoScheduler.java:37` 都没有专用 `TaskScheduler`，`application.yml` 也没设 `spring.task.scheduling.pool.size`（默认池大小 1）。一次缓慢的考试扫描（C9）或慢查询会推迟进程内所有用户的循环待办生成。*修复：* 设置线程池大小或给每个任务独立调度器，并限制单轮工作量。

**C25. 完成循环待办与接续下一期不是原子的。** `TodoController.java:60-70` 先调 `todoService.toggleComplete`（非 `@Transactional`），再调 `recurringTodoService.onTodoCompleted`（自带事务），是两次独立写入。若第二次失败或进程在中间退出，用户就有了一个已完成的本期却**没有下一期** —— 链条静默中断。*修复：* 合并到一个 `@Transactional` 服务方法。

**C26. `ctx.weekOfYear % 2` 是 ISO 日历周奇偶，不是课表的单双周。** `RecurringScriptEvaluator.java:226` 暴露的是 `date.get(IsoFields.WEEK_OF_WEEK_BASED_YEAR)`，而随附的 `SCRIPT_TEMPLATE`（`:257-273`）与 `AGENTS.md:510` 把它当作单双周机制。但应用自身是按课表起始日算教学周的：`firstMonday = periodStartDate.with(previousOrSame(MONDAY)); week = diff/7 + 1`（`WidgetServiceImpl.java:194-196, 202-205`）—— 两者锚点无关。只要学期不是从奇数 ISO 周开始，所有"奇数教学周"规则都会在**错误的周**触发，且 ISO 的 53→1 翻转会在年中改变奇偶。此外 `generateForCustomRules` 没有补扫（不同于 `generateForFixedRules` 的 `MAX_CATCH_UP`），而模板要求的 `ctx.minute === 0` 在 60 秒 `fixedDelay` 漂过分钟边界时会错过时点 —— 没有补扫就意味着周规则可能整整错过一周。*修复：* 暴露课表推导出的教学周（或规则上显式配置锚点日期 + 周期），并让 CUSTOM 规则按 `(lastTriggeredAt, now]` 区间求值并记录扫描游标。

**C27. 自定义规则可每分钟生成一条待办，且所有列表接口都没有分页。** 去重仅靠"同一分钟内不重复"（`RecurringTodoServiceImpl.java:203-207`），因此一个 `return ctx.isWeekend` 这样简单的脚本每天每规则最多生成 1440 条待办 —— 而 `TodoServiceImpl.list`（`:22-27`）无上限返回给每个客户端，小组件每 60 秒轮询一次也同样全量拉取。*修复：* 给规则加显式周期／时间窗限流；给待办与课次列表加分页／`LIMIT`。

**C28. 请求校验留下若干无界字段。** `CourseRequest.weeks` 是 `@NotEmpty List<Integer>`，元素无边界、列表无上限（`dto/CourseRequest.java:12-16`），客户端可传 `0`、负数或 `Integer.MAX_VALUE`；小组件的日期运算 `firstMonday.plusDays((long)(wk-1)*7 + (dow-1))`（`WidgetServiceImpl.java:88-95`）随即抛 `DateTimeException` → HTTP 500，或静默产生学期外的日期。`name`/`title` 没有针对 `VARCHAR(200)`/`VARCHAR(500)` 的 `@Size`（`schema.sql:30,59`），`ddlOffsetMinutes` 有 `@Min(1)` 却没有 `@Max`（`dto/RecurringTodoRequest.java:34-36`），超限值会以数据库错误或 `LocalDateTime` 溢出（500）暴露，而不是 400。课程新增／修改也没有冲突校验，同一日／节次／周次可以放两门课，尽管 UI 宣称有冲突提示。*修复：* 所有映射到列宽度的字符串加 `@Size`；`weeks` 用 `List<@Min(1) @Max(60) Integer>` 并限制元素数；`ddlOffsetMinutes` 加 `@Max`；新增／修改前做显式冲突查询。

**C29. 全局作息表更新对未知节次静默失效。** `PeriodConfigServiceImpl.java:41-57` 对每个提交项调 `updateById` 并忽略影响行数，返回完整列表和 HTTP 200。管理员新增第 13 节时会以为保存成功。提交集合内部的区间重叠或倒序也从不校验。*修复：* 影响 0 行时报错（或有意改为 upsert），并校验提交集合的单调、无重叠区间。

## 八、对初次结论的纠正

以下结论在审查过程中被提出、**经核对后证伪**，记录在此以免他人重复排查：

1. *"`RecurringTodoServiceImpl.delete` 存在跨账号删除"* —— **不可利用。** `recurring_id` 由 `spawnTodo` 服务端赋值，用的既是规则自身 id 也是规则自身 apiKey；`TodoRequest` 不暴露该字段；规则 id 不会被复用。已降级为 C10（防御性加固）。
2. *"`/api/widget/overview/{key}?scheduleId=N` 会返回他人账号数据"* —— **不会。** `scheduleId` 会流入 `scheduleService.getById(...)`/`courseService.listByScheduleId(...)`，二者都校验归属并返回 404。真正的问题是 B2（凭据出现在 URL 中）。
3. *"SSE 流会占用 Tomcat 请求线程 5 分钟"* —— **不会。** `SseEmitter` 立即返回，实际工作跑在 `ai-stream-N` 线程上；真正的池缺陷是 B4。
4. *"模型可调参数不改代码就无法调整"* —— **不准确。** `DeepSeekProperties` 是 `@ConfigurationProperties`，Spring 的宽松绑定会把它们暴露为环境变量；只是没文档、也没写进 `application.yml`。
5. *"README 中 `createDatabaseIfNotExist` 的说法是错的"* —— **不成立**，`application.yml:3` 确实带该参数。只有"需要 `CREATE` 权限"这一前置条件未文档化。
6. *"倒序的考试时间会被持久化"* —— **不会**，`ExamServiceImpl` 会拒绝。

## 九、尚未验证的疑点（需浏览器或运行时环境）

- `TimetableGrid` 只给**已放置**的条目显式 `gridRow`，而把被冲突隐藏的条目记入 `taken` 却不生成单元格，因此当存在重叠课程时，CSS 自动布局游标可能相对节次列错位一行。需要浏览器中用一个重叠对实测；不过无论结论如何，修复成本都很低（给每个单元格显式设置 `gridRow: period.periodNumber`）。
