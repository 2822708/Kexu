# 离线单机 Android 版迁移方案

> 目标：把「大切课程表」做成**数据在手机上、无网可用**的 Android 应用。
> 本文件是设计文档，**不含代码改动**。所有"现状"引用都来自当前代码库
> （`fixed/` @ `8f4f686`），"目标"部分给出可执行的映射与风险。
>
> 日期：2026-09-26

---

## 0. 结论摘要

| 结论 | 说明 |
|---|---|
| 现有后端**不能移植**，只能**重写** | Spring Boot 需要 Java SE 运行时，Android 是 ART；MyBatis-Plus / H2 / jlink 这一套在 Android 上不成立 |
| 但**业务逻辑大部分可翻译** | 83 个后端文件里，真正与框架耦合的是 Controller / Mapper / 配置；核心算法是纯函数 |
| **最大风险不是界面，是定时任务** | 现有"每 60 秒扫描 + 每分钟跑脚本"的语义，在 Android 后台限制下**做不到原样**，必须重新设计并改功能契约 |
| 有一个决定性推论 | 见下一节：**要做到"离线 + 可靠提醒"，就不能走 WebView 复用路线的捷径** |
| 建议先做 PWA | 半天成本、零安卓工具链依赖，先验证"手机上的界面是否可用"，再决定要不要投入数周做原生 |

## 1. 一个决定性推论：为什么不能"套壳 + 把后端塞进手机"

直觉方案是：用 Capacitor 把现有 React 前端打进 App，再把后端逻辑用 TypeScript 重写、数据存 SQLite。
UI 完全复用（32 个前端文件不用改），听起来很划算。**但对"离线单机"这个目标不成立**，原因是：

1. **WebView 里的 JS 无法可靠地在后台运行**。循环待办、考试自动完成这些功能依赖后台定时执行；
   在 WebView 中，页面一旦被切到后台/被系统回收，定时器就停了。
2. **提醒不可靠**。待办 DDL 提醒需要 `AlarmManager` + 通知渠道，这些是原生 API，JS 侧只能通过
   插件桥接触发；一旦插件的"后台唤醒"本身不可靠，提醒就是碰运气。
3. **桌面小组件做不了**。Android 的 `AppWidget` 用 `RemoteViews`，**不能嵌 WebView**，
   现有 `/widget` 页面在安卓上无法复用，必须原生实现。

> 所以：**只要"离线 + 可靠提醒 + 小组件"是硬需求 ⇒ 走原生（Kotlin）路线。**
> 如果只是想"手机上能打开、能用"，那 PWA 就够了，不必做 App。

---

## 2. 两条实现路径的取舍

| | 路径 1：Capacitor + TS 重写后端 | 路径 2：Kotlin 原生（推荐） |
|---|---|---|
| 界面 | **复用现有 React（32 文件不动）** | Compose 重写（约 15–20 个页面/组件） |
| 业务逻辑 | 把 83 个 Java 文件翻译成 TypeScript | 翻译成 Kotlin |
| 数据层 | SQLite（Capacitor 插件）+ TS DAO | **Room** |
| 后台定时 | ❌ WebView 里跑不了，必须靠插件硬撑 | ✅ WorkManager / AlarmManager |
| 待办提醒 | ❌ 不可靠 | ✅ 精确闹钟 + 通知 |
| 桌面小组件 | ❌ 做不了 | ✅ AppWidget |
| 性能 | WebView 内的 SQLite，数据量大时吃力 | 原生 |
| 工作量 | 较小 | 较大 |
| 适用 | 网页版的快速移动壳 | 长期维护的产品 |

**结论：按目标（离线单机）选路径 2。** 路径 1 只适合"我不做 App，只想手机上好用"——那种情况直接用 PWA，
连 Capacitor 都不需要。

## 3. 架构映射（现状 → Android）

| 现状 | Android 对应 | 说明 |
|---|---|---|
| Spring Boot 3.2 + 内嵌 Tomcat | **删除** | 客户端与服务端合并为单进程，不再有 HTTP 层 |
| `controller/`（9 个） | `ViewModel` + `UseCase` | 参数校验从 DTO 注解迁到 Kotlin 校验 |
| `service/` + `service/impl/`（25 个） | `Repository` | 接口/实现两层可合并 |
| `mapper/`（10 个，MyBatis-Plus） | Room `@Dao` | 最大的机械翻译量 |
| `entity/`（10 个） | Room `@Entity` | 字段类型需逐个换算，见第 5 节 |
| `dto/`（15 个） | `data class` | 基本一一对应 |
| MySQL 8 | **SQLite（Room）** | 见第 5 节 |
| `X-API-Key` + `ApiKeyInterceptor` | **删除**（单用户本机） | 若要支持多账号/同步，改用 Android Keystore 保存令牌 |
| `WebConfig`（CORS） | **删除** | 没有跨域概念了 |
| `@Scheduled` × 2 | **WorkManager + AlarmManager** | 见第 6 节，**语义变化** |
| `RecurringScriptEvaluator`（Rhino 沙箱） | 保留 Rhino 或换 QuickJS | 需真机验证，见第 7 节 |
| `DeepSeekClientImpl`（java.net.http + SSE） | OkHttp + SSE | 直接对应 |
| React SPA（32 文件） | Jetpack Compose | 走路径 2 则全部重写 |

## 5. 数据层迁移（逐表 + 逐类型）

### 5.1 表映射

| 现有表 | Android | 备注 |
|---|---|---|
| `api_key` | **删除** | 单用户本机不需要；若做同步则改为本地 `account` 表 |
| `schedule` | `ScheduleEntity` | 去掉 `api_key` 列 |
| `period_config` | `PeriodConfigEntity` | 12 行种子数据：用 `RoomDatabase.Callback.onCreate` 预置 |
| `course` | `CourseEntity` | `weeks` 见 5.2 |
| `exam` | `ExamEntity` | |
| `todo` | `TodoEntity` | 保留唯一索引 `(recurring_id, ddl)` |
| `recurring_todo` | `RecurringTodoEntity` | `script TEXT` 原样 |
| `ai_conversation` / `ai_message` / `ai_action` | 同名实体 | `action_data` 见 5.2 |

### 5.2 类型与 DDL 差异（逐个列出的坑）

| MySQL 写法 | SQLite/Room 写法 | 注意 |
|---|---|---|
| `BIGINT AUTO_INCREMENT` | `@PrimaryKey(autoGenerate = true) Long` | —— |
| `DATETIME`（无时区） | **ISO-8601 文本**（如 `2026-09-26T14:00:00`） | ⚠️ 不要用 epoch 毫秒：课表是"墙上时间"语义，跨时区/夏令时会漂移；ISO 文本在 SQLite 里**字典序即时间序**，可直接 `ORDER BY` |
| `DATE` / `TIME` | ISO 文本（`2026-09-26` / `14:00:00`） | 同上 |
| `BOOLEAN` | `Int`（0/1）+ TypeConverter | SQLite 无布尔 |
| `TINYINT` | `Int` | |
| `JSON`（`course.weeks`） | **`TEXT` + TypeConverter（`List<Int>` ↔ JSON 字符串）** | 见下方权衡 |
| `JSON`（`ai_action.action_data`） | `TEXT` | 本来在 Java 侧就是字符串 |
| `ON UPDATE CURRENT_TIMESTAMP` | **Room 不会自动做** | 必须在 DAO 的每次更新里显式写 `updatedAt`，否则排序/审计会静默失效 |
| `FOREIGN KEY ... ON DELETE CASCADE` | `@ForeignKey(onDelete = CASCADE)` | ⚠️ **SQLite 默认关闭外键约束**，需在 `onOpen` 里执行 `PRAGMA foreign_keys=ON`，否则级联删除不生效 |
| `INDEX` / `UNIQUE KEY` | `@Entity(indices = [...])` | 唯一索引在 Room 里是**约束**，冲突时抛异常（现有代码已优雅处理重复） |
| MySQL 事务（`@Transactional`） | `@Transaction` / `withTransaction` | |

**`course.weeks` 用 Text+Converter 还是建关联表？**

| | Text + TypeConverter | `course_week(course_id, week)` 关联表 |
|---|---|---|
| 改动量 | 小，与现有模型一致 | 中，查询要 join |
| 按周查询 | 需全量加载后在内存过滤 | 可 `WHERE week = ?` 走索引 |
| 适用 | ✅ 一个用户几十门课，内存过滤毫无压力 | 数据量大或要做统计时 |

**建议：先用 Text + TypeConverter**（与现有 `JacksonTypeHandler` 行为一致，迁移风险最低）。
真要优化再演进到关联表。

### 5.3 迁移工具
如果将来要做"服务器 → 手机"的一次性导入：让服务端导出一份 JSON（各表全量），
App 首次启动时写入 Room。**不需要**直接读 MySQL 文件。

## 6. 定时任务重设计（本项目最大的架构风险）

### 6.1 现状语义

| 组件 | 行为 |
|---|---|
| `RecurringTodoScheduler` | 每 **60 秒**扫描一次；启动时补扫停机期间错过的触发（单规则上限 `MAX_CATCH_UP = 5`） |
| `ExamTodoScheduler` | 每 **60 秒**扫描一次；考试结束后把关联待办标记完成 |
| 自定义规则（`CUSTOM`） | **每分钟**执行一次 `shouldTrigger(ctx)` 脚本决定是否触发 |

### 6.2 Android 的硬限制

| 机制 | 限制 |
|---|---|
| `WorkManager` 周期任务 | **最小间隔 15 分钟**；且不保证准时（Doze 打盹、厂商省电策略会推迟甚至砍掉） |
| `AlarmManager` 精确闹钟 | 需要 `SCHEDULE_EXACT_ALARM` 权限（Android 12+）；`USE_EXACT_ALARM` 仅限闹钟/日历类应用（Android 13+）；频繁唤醒耗电 |
| 前台服务 | 可以做到分钟级，但**常驻通知**，用户可见、耗电，且各 ROM 会提示"耗电应用" |
| 厂商 ROM | 小米/华为/OPPO/vivo 默认杀后台，需要引导用户加白名单 |
| `AppWidget` 刷新 | `updatePeriodMillis` **最小 30 分钟** |

### 6.3 重设计方案

**核心思路：把"轮询"改成"事件驱动 + 粗粒度兜底"。**

1. **固定频率规则（DAILY/WEEKLY/MONTHLY）**
   - 不再依赖每分钟轮询：`RecurringScheduleCalculator` 能**预先算出**下一次触发时间 →
     为每个规则挂一个 `AlarmManager` 精确闹钟到点触发一次。
   - 兜底：每次 App 启动/回到前台 + `WorkManager` 15 分钟周期任务各跑一次 `generateDueTodos()`，
     仍然复用现有的"补扫 + `MAX_CATCH_UP` 上限"逻辑（那段是纯函数，可直接翻译）。
   - 这样"停机期间错过的期次"仍然能补，且不依赖持续后台。

2. **待办 DDL 与考试结束提醒**
   - 每条待办挂一个 `setExactAndAllowWhileIdle` 一次性闹钟 → 到点发通知。
   - 考试结束同理（`exam_date + end_time`）。
   - 权限拿不到时**优雅降级**：退化为 `setAndAllowWhileIdle`（不精确），并在设置页说明"提醒可能有几分钟偏差"。

3. **`CUSTOM` 自定义规则** ⚠️ **功能契约必须改**
   - 现状是"每分钟执行脚本判断"。Android 上无法可靠做到。
   - 方案：改为**每次唤醒（启动/回前台/15 分钟周期任务）执行一次脚本**，并把 `ctx` 的语义
     从"此刻"改为"上次检查到此刻的区间"——
     即新增 `ctx.sinceLastCheckMinutes`，同时**保留** `ctx.minute` 但明确其含义为"检查时刻的分钟"。
   - **必须在 UI 和用户手册里写清楚**：类 Linux cron 的分钟级精度在手机上不可保证。
   - 现有 `SCRIPT_TEMPLATE` 里"每逢周五 12:00"这种写法，在"15 分钟粒度 + 精确闹钟"下仍然可用
     （因为固定时刻的触发走的是第 1 条的精确闹钟路径）；真正受影响的是**依赖任意分钟判断**的脚本。

4. **桌面小组件（AppWidget）**
   - **不能放 WebView**，必须原生 `RemoteViews` 重画：左侧课程、右侧待办，用 `RemoteViews` 支持的
     有限控件（`TextView` / `LinearLayout` / `ImageView`，不支持任意自定义 View）。
   - 数据来源直接读 Room。刷新用 `updatePeriodMillis`（≥30 分钟）+ WorkManager + 数据变更时主动推送。

> **一句话总结这一节**：现有后端是"服务端轮询"模型，Android 必须变成"闹钟 + 唤醒补扫"模型。
> 这是**契约层面的变化**，不是实现细节。

## 7. 需要真机验证的风险点（先验证再排期）

| 风险 | 验证方式 | 不通过的退路 |
|---|---|---|
| **Rhino 在 ART 上能否正常工作** | 把 `RecurringScriptEvaluator` 做成一个最小 Android 库，跑现有 21 个单测中的沙箱部分 | 换 QuickJS（需 NDK）或**把自定义脚本降级为预设规则**（每日/每周/每月/月末/双周），功能缩水但可用 |
| 沙箱的 `ClassShutter` / 指令计数在 ART 上行为是否一致 | 真机跑 `RegexVectors` 那套探针 | 同上；或把脚本求值放到 `isolatedProcess` 的 Service 里 |
| SSE 在移动网络切换/断连时能否正确重连 | 真机 + 弱网模拟 | 改为轮询或非流式接口 |
| Doze 模式下闹钟与网络的可用性 | 真机静置数小时 | 引导用户关闭电池优化 |
| 厂商 ROM 杀后台 | 在小米/华为真机测 | 首次启动引导加入白名单 |

## 8. 顺带要一起修掉的历史问题

迁移时**不要把已知缺陷一起搬过去**：

| 编号 | 问题 | 迁移时的处理 |
|---|---|---|
| C26 | `ctx.weekOfYear % 2` 是 **ISO 日历周奇偶**，不是课表教学周 | 新的脚本上下文应改为暴露**课表推导出的教学周**，或接受"锚点日期 + 间隔"参数；否则"双周课"会算错 |
| A1 | 沙箱超时无法终止原生调用 | 若保留脚本功能，建议直接在 `isolatedProcess` 里跑，从根上解决 |
| C1 | 未绑定课表时 COURSE 指纹退化为常量 | 单机版没有多课表串数据的风险，但要保留"操作必须指定课表"的校验 |
| C2 | 提案并发重复执行 | 单机单线程，风险降低，但 Room 事务仍要写对 |
| C3/C4 | 提案失效逻辑未按工作空间隔离 | 单机只有一份工作空间，可简化 |

## 9. 安全与密钥

| 项 | 现状 | Android 做法 |
|---|---|---|
| DeepSeek API Key | 环境变量 / 本机 `settings.properties` | `EncryptedSharedPreferences`（AndroidX Security）或 Keystore 加密后落盘 |
| 登录凭据 | `X-API-Key` 存 localStorage | 单机版**不需要**；若保留服务器同步，用 Keystore 保存 |
| 沙箱 | Rhino 进程内沙箱 | 若保留，建议独立进程（顺便解决 A1） |
| 明文 HTTP | `http://localhost` | 访问远程 DeepSeek 走 HTTPS；若将来连自建服务器，Android 9+ 默认禁明文，必须用 HTTPS |

> 注意：**"离线单机"不等于"完全无网"** —— AI 功能（自然语言增删改、HTML 课表解析）仍然需要网络调用
> DeepSeek API。离线的是课表/待办/考试这些核心数据。这一点要在产品文案里讲清楚。

## 10. 分阶段计划

| 阶段 | 内容 | 预计 | 产出 |
|---|---|---|---|
| **Phase 0** | 前端加 PWA（manifest + service worker + 图标 + 离线缓存） | 0.5 天 | 手机浏览器可"添加到主屏幕"、已看页面离线可开；**顺便验证手机上的界面是否可用**；桌面版与浏览器版同时受益 |
| **Phase 1** | Kotlin 工程骨架 + Room 数据层 + 核心页面（课表网格、课程 CRUD、待办、考试、作息表） | 1.5–2 周 | 能离线记录与查看课表 |
| **Phase 2** | 循环待办（固定频率）+ AlarmManager 精确提醒 + WorkManager 补扫 + 通知渠道 | 1 周 | 核心时间管理闭环可用 |
| **Phase 3** | AI 对话（OkHttp SSE + Compose 聊天 UI + 提案卡片 + 一次性确认） | 3–5 天 | 与网页版功能对齐（除脚本） |
| **Phase 4** | 原生 AppWidget 桌面小组件 | 3–5 天 | 替代现有 `/widget` 场景 |
| **Phase 5** | 自定义脚本（先验证 Rhino，不行换实现）+ 可选服务器同步 | 1–2 周 | 功能完全对齐 |

**关键路径**：Phase 0 验证可行性 → Phase 1 的 Room 数据层是最大机械工作量 → Phase 2 的定时任务是最大设计风险。

## 11. 建议的 MVP（先打通这条链路验证三个未知）

不要一上来做全功能。先做一个最小切片：

```
课表网格（Compose）
   + 课程增删改查
   + Room 落盘
   + 一个原生 AppWidget
```

它一次性验证了**三个最大的未知**：
1. Room 数据层能否干净地承接现有模型（含 `weeks` 与时间类型）
2. Compose 渲染 7×12 网格 + 跨节行合并是否可行（现有 `TimetableGrid.tsx` 的 `rowSpan` 逻辑要重写）
3. AppWidget 的 `RemoteViews` 能否呈现现有 `/widget` 的信息密度

这三个通过了，剩下的都是体力活；任何一个不通过，都要回到方案层重新决策。

## 12. 明确不做的事

- ❌ **不把 Spring Boot 塞进 Android**（不存在可行路径，别浪费时间找）
- ❌ **不用 WebView 套壳来做"离线单机"**（后台与提醒不可靠，小组件做不了）
- ❌ **不直接复用 MySQL 的 `schema.sql`**（JSON 列、`ON UPDATE CURRENT_TIMESTAMP`、外键默认行为都不同）
- ❌ **不承诺"分钟级"的循环触发精度**（Android 平台不允许，要在 UI 上如实说明）
- ❌ **不在没有真机验证 Rhino 的前提下把自定义脚本排进关键路径**（它是唯一可能推翻排期的技术未知）
