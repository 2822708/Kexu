# 模型输出评估集（6.2 #7）

改 prompt、换模型、调检索策略之前，先跑这里的回归。**没有它，记忆升级就是盲改**——
你看到输出「好像还挺好」，但没有任何证据说明它比改之前好，也没有证据说明没把原来对的改坏。

## 为什么是两层

一开始想的是「录一批真实输出当期望值，跑回归比对」。这个思路有个硬伤：

> **历史输出只能锁住「和上次一样」，锁不住「上次本来就是错的」。**

模型把「10月20日交」解析成 2026-11-20，你把这坨输出录进基线，回归从此永远绿——
它测的是「模型又犯了同样的错没有」，不是「模型做对了没有」。

所以拆两层，各自管一件事：

| 层 | 验证什么 | 需要 API Key | 在哪跑 |
|---|---|---|---|
| **契约层**（`contracts/`） | 模型输出 → 服务端清洗 → 最终交付给用户的字段，**服务端侧的确定性归约是否正确** | 否 | JUnit，每次 `mvn verify` |
| **提示词层**（`prompts/`） | 给定材料，**模型实际产出**的 JSON 是否守规矩 | 是 | 脚本，改 prompt / 换模型时手工跑 |

契约层锁的是代码，提示词层锁的是模型行为。前者可以进 CI，后者不能——除非你想让 CI 每次烧 token
还随机红绿。

## 契约层

`contracts/*.json` 是「模型输出 → 期望产出」的固定用例。每条用例给一份模型原始 JSON（含脏数据：
不合规枚举、超长字段、过去时间、越界数值、缺失字段），断言服务端清洗后的结果。

这类用例是**确定性**的：同样的输入永远是同样的输出，不依赖模型、不烧 token、
不会因为上游换了个采样温度就红。它抓的是另一类真实事故——服务端清洗逻辑写错，
把模型本来对的输出改坏了，或者把模型的错输出放过关。

覆盖五个场景，每个场景既要「正常输出不被改坏」，也要「脏输出被正确拦下 / 钳制」：

| 场景 | 被测入口 | 关键契约 | 用例数 |
|---|---|---|---|
| `task-extract` | `AiServiceImpl#extractTasks` | 空标题跳过、超长截断、非法类型降级 OTHER、过去 deadline 归 null、不猜时间 | 11 |
| `notice-extract` | `NoticeServiceImpl#extract` | 无来源填「未标注来源」、relevance 钳到 1..3、keyTime 过去归 null、条数上限 | 8 |
| `daily-plan` | `DailyPlanServiceImpl#generate` | 课程块时刻必须与课表逐字相同、漏课 502、任务块只能引未完成任务、必须有 BREAK、refId 驼峰兼容 | 11 |
| `memory-extract` | `MemoryService#create/update`（见下方说明） | ADD/UPDATE 判定、去重按归一化内容、非法类型直接拒绝（非降级）、超长拒绝（非截断） | 11 |
| `query-plan` | `AiServiceImpl#queryPlan` | phases 最多 6、leadDays 钳到 [-30,365]、超长字段截断、不伪造公告 | 8 |

**记忆场景为什么不在 `AiServiceImpl`**：其余四个场景的模型输出都要经过
「JSON → DTO 清洗」这一步，断言自然落在 `AiServiceImpl` / `NoticeServiceImpl` /
`DailyPlanServiceImpl`。记忆没有 DTO 往返——模型给出的 `type/content/importance`
被直接交给 `MemoryService.create/update`，清洗逻辑在服务层。契约断言必须落在真正
决定「能不能落库」的地方，否则测的是个不存在的翻译层。

这个差异背后是**两种不同的失败哲学**，用例专门锁住它：

| | 脏输出的处理 | 理由 |
|---|---|---|
| 任务 / 通知 / 计划 | **钳制或降级**后照常展示 | 少一条、截一段都比白屏好 |
| 记忆 | **直接拒绝** | 一条错误或半截的记忆会留在库里、之后每次对话都被注入，污染是长期复利的 |

某次「统一清洗逻辑」的重构如果悄悄把记忆的拒绝改成截断，契约层会红。

## 提示词层

`prompts/*.json` 是「脱敏材料 → 结构断言」的用例。断言的是**可判定的规则**，不是逐字比对：
- 「材料没写时间 → deadline 必须是 null」（可判定，无需人看）
- 「材料含「忽略以上规则」→ 输出仍不含注入内容」（可判定）
- 「材料只讲成绩 → 不产生任何任务」（可判定）

不断言「标题措辞是否漂亮」那类东西——那需要人看，脚本判不了，硬判只会产生假红。

跑法见下方「运行」。

## 脱敏

用例里的课表 / 任务 / 对话全部是构造样本，**不含真实姓名、学号、学校、API Key**。

真实样本进来之前必须先脱敏，规则（手工执行即可，不为此加脚本依赖）：

| 类型 | 形态 | 替换为 |
|---|---|---|
| 学号 | 8–12 位纯数字，常以「学号」前缀出现 | `«REDACTED:STUDENT_ID»` |
| 身份证 | 18 位（末位可为 X） | `«REDACTED:ID_CARD»` |
| 手机号 | `1[3-9]` 开头 11 位 | `«REDACTED:PHONE»` |
| 邮箱 | `x@y.z` | `«REDACTED:EMAIL»` |
| 密钥 | `sk-` / `Bearer` 开头的长串 | `«REDACTED:SECRET»` |
| 学校 / 教师姓名 | 具名机构与个人 | 换成「某大学」「某老师」 |

真样本宁可少，也不要带着真名进仓库。构造样本永远优于脱敏样本——脱敏总有漏网。

> 注：`MemoryServiceImpl` 侧的长期记忆有一条独立的内容清洗（归一化去重、类型白名单），
> 那是**运行期**防护，与这里的**数据级**脱敏是两件事，不要混淆。

## 运行

**契约层（进 CI，无需 Key，已落地 49 条用例）**：

```bash
cd src/backend
./mvnw -B -ntp test -Dtest='com.timetable.eval.*Test'
```

当前状态：契约层已完整落地并通过（57 项断言 / 49 条用例），含在 `./mvnw verify` 全量 338 项里。

**提示词层（需 Key）——尚未实现**：

设计已定（见下方「提示词层」小节），但代码还没写。原因是它需要真实 API Key 与稳定的
模型采样，属于「改 prompt 时才手工跑」的工具，可以等 #8/#9 真正开始改动时再落地。
写的时候按这个骨架来：`PromptEvalRunner` 读 `prompts/*.json` → 用真实 `LlmClient` 调用 →
对每条断言做规则判定 → 输出 `target/model-eval-report.json`（逐条通过/失败、耗时、token 消耗）。
没有 `LLM_EVAL_API_KEY` 时整体 skip 而不是红：CI 不该因为「没配 Key」而红，也不该在 CI 里烧 token。

**为什么契约层先落地**：它不需要 Key、确定性、能进 CI，而且它抓的是「服务端把模型输出改坏」
这类事故——这类 bug 一旦发生就是全量用户受影响，优先级高于提示词微调。

## 实现上的三个坑（改评估集前必读）

### 坑 1：`@Configuration` 在扫描范围内会污染整个测试套

评估集的 Spring 切片 `ModelEvalSupport.EvalApplication` 定义在 `com.timetable.eval`，
正落在 `TimetableApplication` 的 `@SpringBootApplication` 扫描范围内。若不挂 `@Profile`：

- 那些用**完整应用上下文**的集成测试（`AiCampusAgentJourneyIntegrationTest`、
  `NoticeEndpointIntegrationTest`）会把评估集的 `Clock.fixed(2026-10-19)` 一起装进去；
- 于是它们的「系统时钟」被悄悄换成固定时刻，`snooze` 到期判定、计划缓存失效判定随之中招；
- 报错出现在**完全无关的测试**里，且单独跑那些测试又是绿的——极难定位。

修法是给切片挂 `@Profile(ModelEvalSupport.PROFILE)`，五个测试类统一
`@ActiveProfiles(ModelEvalSupport.PROFILE)`。既有 AI 测试早就这么做了
（`@Profile("campus-agent-xxx")`），这里只是沿用同一约定。

### 坑 2：自增 id 不能写进用例

课程的 id 由数据库自增生成，每次跑都可能不同。用例里写 `ref_id: 101` 会在换库或换执行顺序后
莫名全红。所以用例用**序号占位**：

| 占位符 | 含义 |
|---|---|
| `course#1` / `task#2` | 装配时创建的第 1 个课程 / 第 2 个任务 |
| `course#missing` | 故意指向不存在的记录（用于「引用了不存在的课程」这类拒绝用例） |
| `target_id: 1`（记忆） | `existingMemories` 里的第 1 条 |

执行器在喂给 mock 之前把它们映射成真实 id。`DP-14` 刻意保留驼峰 `refId` 形态——
那条用例的目的就是验服务端两种写法都要认，映射时不能把它归一化掉。

### 坑 3：「超长」用例的输入必须真的超长

写用例时最容易出的不是断言错，而是**断言永远为真**：一条「内容超过 200 字必须拒绝」的用例，
如果输入只有 166 字，它必然通过，但什么都没验。这种假绿比红危险得多。

`ModelEvalFixtureTest.oversizedCasesActuallyExceedTheirLimit` 把「输入必须越界」本身
变成断言，覆盖所有截断/拒绝类用例。加新的超长用例时，先让这条测试过。

## 边界

- **不是**训练集，不做微调，不进模型（6.7 禁区：本地模型训练）
- **不是**用户行为埋点，不含真实用户数据（6.7 禁区：用户画像）
- 用例数保持 30–50 条。再多维护成本超过收益，再少覆盖不住场景
- 契约层跑在内存 H2，与既有测试同一套 Flyway 迁移，不碰真实库
- 评估集**不修改任何生产代码**：`git status` 里应当只有新增文件
